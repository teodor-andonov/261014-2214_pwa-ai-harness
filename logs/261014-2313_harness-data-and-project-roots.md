# Harness data versus project folders — 14 October 2026

## Clarification / decision
The **first selected folder is the harness data root**, not a managed-project container. Every persistent item belonging to the harness itself must live there: conversations, attachments, mode prompts and permissions, project metadata, preferences, indexes and logs generated by the running app. The application code, installer and browser cache are not sources of truth.

**Projects are separate references** to existing local filesystem locations (as in Codex). Each project can have **one or multiple authorised folders**, potentially on different drives. Project folders do not get moved or copied into the harness data root. The root stores only project descriptors, original folder locations, relative mappings if feasible, and folder/tool permissions. All file access must be enforced in the trusted backend, not merely by the mode prompt.

## Portability
Copying the harness data root to another computer restores harness state. External project contents are not part of this copy; if their paths differ, the app should show missing roots and allow relinking without losing chats or project metadata. Folder permission grants need revalidation when root paths are remapped. Do not silently authorise new paths.

## Current implementation versus target
Prototype 02 currently supports one external folder per project, **and also includes an internal/managed-project option**; the latter contradicts the new project-structure direction and should be removed from the normal project creation flow. Multi-folder project grants and path relinking are not implemented yet.

## Launcher explanation
`start.cmd` is only a Windows batch launcher. It checks Node availability, opens the localhost URL and starts the Node server that provides PWA assets plus filesystem/auth/agent services. It is **not the PWA**, an internet host, or an app data location. Closing its terminal stops the backend. A future tray service, packaged Tauri app or equivalent can eliminate the visible command prompt without changing the basic frontend/runtime architecture.

## Next implementation steps
1. Split harness root storage from project roots in API and data schema, with project `roots: [{path, permissions}]` and stable project IDs.
2. Make the UI support linking, adding, removing and reauthorising one or more folders per project; add missing-path relinking.
3. Enforce resolved path scope and per-root permissions for each tool action (including symlinks, junctions and file changes between check and operation).
4. Preserve all harness settings/chats/modes in selected root; no silent persistent state in local app files.
5. Keep the startup script as a development convenience; assess a less visible packaged launcher when the architecture is stable.

## Verification state
